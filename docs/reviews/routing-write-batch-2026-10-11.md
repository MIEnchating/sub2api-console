# 调度写回：批量确认与重复请求（2026-10-11）

本轮承接全局审查的第一个待办模块 `routing / routingwrite`。日志保持冻结。保留 `12a3d80` 上的既有工作区改动，生产代码变更仅在 `backend/internal/routingwrite/batch.go`，新增回归放在该模块 `__tests__/`。

## 已复现并修复

1. **正常批量结果被误判为歧义。** 只有 `id` 的逐项结果因 `fmt.Sprint(nil)` 产生 `<nil>`，未能使用备用 ID；同时存在 `success_ids` 和 `results` 时，一致的确认也被当成重复。两账号隔离接口回归均复现额外两次 GET。现在允许不同响应字段表达同一结果；同一字段重复 ID、相反结果、非法或未知 ID 仍须读回。
2. **逐项失败原因丢失。** `failed_ids` 与逐项失败同时存在时，原实现退回读取并覆盖接口的具体拒绝原因。现在合并一致失败并保留逐项错误。
3. **两个 ID 字段互相矛盾仍被接受。** 同时返回 `account_id=41`、`id=42` 时，原实现直接接受前者，回归中账号 41 实际未变也报告成功。现在拒绝该确认，重新读取核对；无效的显式 ID 不能通过备用字段绕过校验。
4. **歧义确认串行等待。** 原实现逐项同步 GET。现在每个批量结果最多启动配置并发数的读回 worker，全部共享原有 HTTP 并发门限，并等待完成后释放账号租约。测试通过请求开始/释放事件验证并发为 2，取消后所有未确认结果失败，不以耗时阈值证明提速。
5. **完成读回后再读取全目录。** 开启写后验证时，即使歧义结果已逐项读取并确认，仍拉取全量账号目录。先复现两次逐项读回加一次列表读取，再改为仅核验尚未读回的成功写入。明确开启验证的普通批量确认仍必须读取目录，未实际生效的字段仍失败。
