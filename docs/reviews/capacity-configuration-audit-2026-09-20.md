# 并发范围与健康账号分配审查

本轮修复以用户确认的规则为准：严格遵守上游总额度；有可用额度时优先已确认健康账号，真实额度不足时保留「等待并发额度」并说明原因。

| 问题                                   | 修复行为                                                           | 回归范围                                            |
| -------------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------- |
| 退出共享范围后仍被旧暂停或全局门禁限制 | 按当前有效范围恢复普通调度；范围外账号保留配置容量                 | routing / routingwrite 的 scope exit 用例           |
| 多分组开关判断不一致                   | 计算、写入、开户按稳定主分组判断                                   | capacity_scope_membership                           |
| New API 意外参与 Sub2API 共享限制      | 共享范围只适用于 Sub2API；自身开启扩容时仍遵守扩容配置             | capacity_health_release / capacity_scope_membership |
| 自动熔断停用后仍占满额度               | 本地及远端确认自动停用后释放预留；保留人工控制和未确认状态         | capacity_health_release / allocation_scope_exit     |
| 健康账号被无健康证据账号挤占           | 容量不足时优先已确认健康账号；确认暂停释放后才恢复                 | capacity_health_release                             |
| 多上游分别计算全局余量造成饥饿         | 先规划各上游共享的全局份额，保留零份额，按真实上游额度重新分配余量 | capacity_health_release                             |
| 共享下调绕过已开启扩容的写入和步长设置 | 独立分配路径不替代已启用的扩容路径                                 | capacity_scope_membership / allocation_scope_exit   |
| 新增账号漏算范围外预留或全局限制       | 预览先扣除受保护预留，提交在容量租约内重新读取并校验               | onboarding allocation_scope                         |

熔断账号是否恢复仍由健康状态机决定。计划中的下调不能提前用于扩容，必须读回确认。全局与分组智能扩容都关闭时，不启用全局并发上限。

本轮后端发布候选、源码校验值、隔离测试结果、数据库备份及运行核对记录保存在服务器 `/root/sub2api-deployments/capacity-configuration-audit-20260920/`。保留已上线账号工作台与成本告警更新；运行服务发布不更改用户策略，不直接改写生产账号状态。
