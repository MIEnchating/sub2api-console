# 持续发现、稳定排位与满载恢复（2026-09-16）

接续 [调度问题修复记录](scheduling-policy-fixes-2026-09-16.md)。本轮目标是持续发现价格、速度、稳定性更好的账号，并减少模型满载导致的连接重建。Console 负责后续流量调度，Sub2API 网关负责当前请求在安全边界内恢复。

## 策略含义

各策略原有健康门控、成本墙与业务保护保持生效。

| 策略 | 价格、速度与稳定性的侧重 |
| --- | --- |
| 价格优先 | 价格 80%，速度 20% |
| 速度优先 | 速度 80%，价格 20% |
| 均衡 | 价格与速度默认各 50%，可配置比例 |
| 稳定性优先 | 稳定性 75%，速度 15%，价格 10% |

以上比例作用于归一化后的质量分，最终还乘健康门控，并非直接分配流量比例。

## 稳定排位

- 从已经在远端生效的优先级出发，保留现有槽位。新增、退出成员不再整体重编号。
- 普通晋升要求足够有效成功证据和超过阈值的收益，沿用最低样本数、变更阈值、冷却配置。默认最低 5 个样本、10% 收益阈值、60 秒写入冷却。
- 与当前位置之后的所有候选比较，解决相邻的小幅差异挡住明显更优候选的问题；晋升不得跨越对其明确更优的账号，防止价格、速度、健康三方取舍在相同证据下循环换位。
- 换位前统一检查涉及账号的冷却，避免只撤销一方目标造成重复优先级。确认退化的账号及时让位；待确认异常保留温和处置。
- 共享并发不足时，暂停与保留顺序也使用稳定比较。容量确认、人工保护、管理范围与写入开关仍由原保护层执行。
- 多分组仍聚合各组策略和预算贡献，稳定主分组负责唯一写回；缺失倍率不制造低价优势，不可比较的速度不制造快账号优势。

实现集中在 `backend/internal/routing/stable_placement.go`，回归在 `routing/__tests__/stable_placement_test.go`。包括真实计算与读回后的多轮保位、冷却、退化、共享容量及副分组策略影响。

## 持续发现

新增 `probe.performance_exploration_enabled`，页面名称为「持续评估候选速度」，默认开启。在已有探测范围内，在用账号也按既有间隔提供参考探针；关闭后恢复有新鲜流量时跳过的原有行为。参考探测会增加上游请求，不绕过主动探测总开关、暂停、成本墙、人工保护、分组设置或每轮 `concurrency × 8` 批次上限。

排位比较优先使用双方同模型且足量的真实流量。真实数据不足时，可使用双方完全可比较的独立探针：

- 请求模型、实际模型、协议、提示指纹、真实请求体指纹必须一致。指纹不含凭据、URL 或原始提示词。
- 仅成功的一次请求、实际测得的流式首字参与。重试恢复、缺失实际模型、完整 JSON 的总耗时不构成性能优势。
- 最新观察必须仍新鲜，历史连续样本受评分回溯范围限制。失败、配置变化、无效性能测量或超过有效探测间隔与新鲜期上限的空档会中断系列；不能拿隔夜成功配一条当前样本抢位。
- 达到最低样本门槛才比较；探针速度比值最多按 2 倍且不超过配置上限。共享模型多于一个时采用对挑战者最不利的速度比。
- 界面 P50/P95 仍仅展示真实流量。常规性能权重与独立的探针排位证据分开处理。

流量和探针各自保留每账号最多 200 条，避免高流量立即挤掉参考探针；晋升读取范围覆盖最低样本门槛，即使门槛高于评分数量窗口也可达到。探针按模型分别取样，但总保留量仍为每账号 200 条；配置的模型数和最低样本数过高时，可能无法积累足量可比较证据，此时保留排位。样本按稳定证据 ID 去重，不把同一请求的补齐当作新证据。

有新鲜流量时，额外性能探测失败保留来源错误并继续本轮调度；只有健康判断确实依赖探针时，严格回退策略才会中止，避免可选探测阻塞已有健康流量。

关键回归：`routing/__tests__/probe_performance_test.go`、`probe/__tests__/performance_evidence_test.go`、`evidence/__tests__/performance_exploration_test.go`、`business/__tests__/probe_exploration_policy_test.go`、前端 `features/policy/__tests__/probe-exploration.test.tsx`。

## 当前请求恢复

网关改动在相邻工作区 `/root/workspace/sub2api`。除 HTTP native/passthrough 的既有输出前恢复外，补齐 Responses WS 的 HTTP bridge、ctx_pool 与 passthrough 首轮满载恢复：先暂存元数据，明确未输出时进行有限同账号重试或换号，成功后仍使用原客户端连接。HTTP bridge 与 ctx_pool 后续文本轮次可使用已重建的完整当前轮次安全重试。

已出现文本或工具调用输出，或上游报告了正用量时，不透明重放；含工具结果的新增重放路径保守拒绝。passthrough 后续轮次缺少可确认的完整历史，保留原来的失败语义。所有上游持续满载、已输出后失败或无法安全重建上下文时，仍可能返回错误，不能承诺消除所有重连。

WS 满载重试有跨账号的 30 秒启动窗口，并继续服从已有次数与换号限制；该窗口限制新尝试的启动时间，成功请求仍按正常读取超时运行。客户端断开会取消等待和新尝试；ctx_pool 与 passthrough 已输出轮次保留原有最多 1200ms 的用量回收，服务端或租约取消立即结束。

首输出前暂存会延后 `response.created` 等元数据，失败尝试的响应 ID 不会返回客户端。passthrough 在首输出前仍及时转发无 ID 的取消指令；已接受的取消或会话更新等控制帧会关闭本次自动重放资格，后续轮次按原响应 ID 取消的行为保持不变。每次尝试结束后等待其客户端队列读取退出，再进入重试。

已经收到上游元数据后的超时或连接中断属于执行结果不确定，不会因为元数据被暂存而新增透明回放；明确的满载拒绝才使用本轮新增恢复。输入、输出、缓存、推理、图片和音频等正用量均阻止重放；被暂存或抑制的前序帧也参与累计判断，不依赖失败结束帧再次携带用量。已读到的结束帧在转发元数据失败时仍保留原错误归因与用量，只结算一次；只读取内存中已暂存的剩余帧，不因此追加网络读取或请求重放。
