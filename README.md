# Sub2API Console

Sub2API 的独立可视化控制面。业务规则全部由 Go 后端领域服务执行，`sub2api-skills` 只作为流程和策略参考，不是运行时依赖。当前版本提供账号与分组管理、上游同步、鉴权恢复、探活巡检、调度写回、告警、开户、运行历史和请求追踪；浏览器不会直接接触 SQLite、Admin Key、Token 或密码箱。

开户自动获取模型时，优先调用 Sub2API 管理端模型同步预览接口；接口失败或未返回可用模型时，使用本次开户的 Base URL 和上游 Key 请求 `/v1/models` 兜底。兜底必须返回业务成功且非空的模型列表；两条路径均失败时保留待续记录，重试复用已有 Key。已配置分组模型列表时继续使用配置值。

添加账号的确认弹窗支持按上游分组获取并多选探活模型，每个待新增账号最多选择 20 个；也可切换为手动填写，每行一个。留空的账号沿用分组或平台默认模型。同一上游分组共享获取的模型列表，批量添加时各账号分别保存自己的选择；已有账号的绑定更新不修改探活模型。模型列表由 Go 后端任务读取，任务结束前清理本次创建的临时 Key，不复用或清理探活弹窗的临时凭据，也不发送生成请求。配置由 Go 后端校验并随新增账号一起保存，保存配置不会立即发起探活。

确认弹窗还支持为每个新增账号单独添加「请求模型 → 上游模型」映射，最多 100 条，仅接受精确模型名。上游模型通过统一的「获取模型」入口读取一次，映射与探活选择共用结果，同一上游分组的多个账号也复用该列表。选择上游模型后两侧自动回显同名模型，请求模型名称可修改；更换上游模型时保留已自定义的请求模型。留空保留自动同步或分组配置生成的同名映射；填写后新增请求模型别名或覆盖对应同名规则，其余模型保留。映射由 Go 后端校验并写入账号的 `credentials.model_mapping`，本地模型目录同步包含请求模型别名；已有账号绑定更新不修改映射，待续开户时也不能更换首次确认的映射。

## 技术栈

- 前端：React 19、TypeScript、Rsbuild、Bun、TanStack Query、Tailwind 风格 CSS、Lucide
- 后端：Go 1.26、Gin、modernc SQLite、标准库 HTTP Client
- 业务数据：只使用 Console 自有 `data/sub2api-console.sqlite3`
- 业务 API：Console 自己的 Admin API 客户端，远程写操作统一读回并审计
- 任务状态：Console 自己的 `data/tasks.sqlite3`，与业务数据分离
- 业务任务：Go 任务执行器 + Console 任务库，按领域服务执行
- 实时任务：Go 调度器 + SSE
- 领域服务：`internal/inspection`、`internal/probe`、`internal/authrecovery`、`internal/upstreamsync`、`internal/routing`、`internal/notification`；外部网络调用均通过受控适配器进入。

页面入口：运营总览、账号管理、上游管理、分组调度、调度策略、自动巡检、Uptime Kuma、日志中心、告警与通知、告警策略、请求查询、密码箱和系统设置。

页面首次加载使用结构骨架；编辑、详情和选择弹窗统一使用转圈与可见读取提示，读取期间允许取消并阻止提前保存。任务尚未返回时不显示虚构进度，后台刷新保留已有内容。开发及逐模块核对记录见 [加载交互规范](docs/loading-interactions.md)。

## 后台任务并发

系统设置「任务并发」（`/config?tab=tasks`）展示各模块并发上限、运行数和等待数，状态每 10 秒刷新。各模块独立使用等待队列；上限和每个模块的队列容量均可在页面修改（1–10000），保存后立即生效并持久保留。降低上限不取消已有任务，已有任务完成后按新上限调度；降低队列容量不丢弃已接收任务，队列腾出空间后才接收新任务。

页面保存值优先于启动环境变量；尚未保存时，使用 `SUB2API_TASK_CONCURRENCY_<模块名>` 与 `SUB2API_TASK_QUEUE_CAPACITY`（默认 100）或内置默认值。后台维护和模型自动检测调度包含常驻任务，运行数包含这些任务。这里控制 Console 后台任务池，不修改 Sub2API 上游用户额度或账号并发。页面保留编辑草稿，版本冲突时需重新读取后再保存。

## 账号请求与用量

请求查询展示稳定账号 ID、请求 ID、输入及输出 Token、缓存读取及写入 Token；流量排行可按时间范围、账号分组和平台查看已采集请求的账号汇总。统计来自后端采集到的上游记录，受上游日志完整性、采集范围及保留时间影响，不代表上游未提供的请求也已入库。

上游明确上报的零值保留为零，未上报的 Token 字段保留未知；缓存读取或写入可以独立于输入输出用量存在。汇总仅累计已提供的字段，同一账号与请求 ID 的重复流量记录不重复计数；这些统计用于运行观察，不作为计费账单。

## Uptime Kuma 接入

Uptime Kuma 接入配置位于系统设置「监控平台」（`/config?tab=monitoring`）。Uptime Kuma 菜单包含三个独立页面：监控管理（`/uptime-kuma`）、功能模板（`/uptime-kuma/templates`）和状态页管理（`/uptime-kuma/status-pages`）。页面通过侧栏导航，不提供页头互跳；配置保存与断开操作位于页头，管理列表使用通用表格、筛选、分页和行内操作，编辑在通用弹窗中完成。通知渠道及维护计划的控制台页面和管理接口已移除，远端已有配置保留。

在「Uptime Kuma → 接入配置」填写服务地址与 Uptime Kuma 设置中创建的 API 密钥。支持输入实例根地址或以 `/dashboard` 结尾的仪表盘地址，保存前会验证 `/metrics` 接口。官方 API 密钥通过 HTTP Basic Auth 的密码字段读取指标，本身没有监控项管理权限。

需要管理监控项时，同时填写仪表盘账号和密码；已启用两步验证的账号还需填写当前 6 位验证码。Go 后端通过原生 Socket.IO / Engine.IO 4 WebSocket 接口登录并保存会话。反向代理必须允许 `/socket.io/` 的 WebSocket 升级。登录会话失效后重新输入密码和当前验证码并保存，不会自动重放写请求。地址、密钥、密码和登录会话保存在后端私有配置库，API 只返回地址、账号、配置状态和版本；验证码不持久化。更换地址必须重新输入对应实例的密钥及管理凭据，禁止把旧实例的凭据自动发送到新地址；连接不跟随重定向。

- 只配置 API 密钥：查看监控状态、响应时间、证书有效期和上游提供的 24 小时在线比例，每分钟刷新。暂停项可能不在指标中，旧版没有提供的指标显示「暂无数据」。旧版 `/metrics` 不带稳定监控 ID 时仅展示数据，不通过名称绑定管理目标。
- 监控管理：新增 HTTP(S)、HTTP 关键字、TCP、Ping、DNS、Push 和分组；页头提供独立「新增分组」入口，分组表单仅设置名称及所属分组，支持子分组；编辑名称、地址、检测及重试间隔和分组。HTTP 支持请求方法、请求头、请求体、状态码范围、重定向、TLS 和 Basic/Bearer 鉴权。已有敏感字段留空保留，可显式清空；编辑不能改变类型，分组调整校验循环引用，已有通知关联保留。监控列表按稳定父组 ID 展示可折叠的层级，支持分组筛选；搜索和状态筛选保留匹配子项的父组，跨页仍显示完整所属分组。Push 上报地址仅在详情中按需读取，不进入常规列表或浏览器持久存储。
- 功能模板：保存监控类型、地址、检测间隔、正常状态码、超时、重试参数、TLS 忽略、反转判断，以及请求方法、请求头、请求体和编码。监控地址填写服务地址，选择接口模式后自动补全 Messages、Chat Completions 或 Responses 路径；切换模式时保留网关前缀和查询参数，不重复追加 `/v1`。列表只返回摘要，编辑时通过受鉴权保护的 no-store 详情接口回显请求头和请求体，关闭弹窗清理查询缓存。请求头默认留空，不以示例充当默认内容；模板编辑不提供独立鉴权方式，保存时清除旧模板的独立鉴权配置，需要认证时可填写请求头。已有监控不随模板修改而改变，监控表单仍可独立设置鉴权，不再提供「使用模板鉴权」选项，选择或切换模板保留已填的监控鉴权信息。套用 JSON 请求模板时可单独填写请求模型，留空沿用模板；Go 后端仅替换当前监控请求体的 `model` 字段，保留消息、请求头和其他参数，不改写模板。
- 内置请求模式：Claude Messages（`/v1/messages`）、OpenAI Chat Completions（`/v1/chat/completions`）、OpenAI Responses（`/v1/responses`）及 Claude CLI。选择模式时由 Go 后端生成预设并填入可编辑请求体，后续保存以当前文本为准，不再覆盖修改；请求模型和发送消息提供独立输入，修改会同步到请求体；原始请求体默认收起，可展开查看或编辑，复杂内容只修改对应字段并保留其他参数。标准模式不自动填入请求头，直连 Claude 需自行设置 `anthropic-version`；显式选择 Claude CLI 会填入其专用请求头。请求体编码支持 JSON、表单（x-www-form-urlencoded）和 XML，套用时传递至 Kuma 的 `httpBodyEncoding`；JSON 内容会校验。默认预设非流式、输出上限 16 token，OpenAI 使用 `store=false`。请求规范参考 [Claude Messages](https://platform.claude.com/docs/en/api/messages/create)、[OpenAI Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)、[OpenAI Responses](https://developers.openai.com/api/reference/resources/responses/methods/create)。
- 状态页：新增、编辑和删除，配置标题、路径、说明、主题、域名、页脚、标签及证书显示，管理公开分组及监控项顺序。编辑保留原路径和未修改的展示设置；公告、历史事件、外观高级配置及尚未提供专属表单的监控类型仍在原仪表盘管理，不表示覆盖 Uptime Kuma 的全部原生功能。
- 暂停、恢复和删除需要确认目标及 ID；非空分组需先移出子项再删除。配置版本或监控项基本信息发生变化时，旧页面的写入会被拒绝，需刷新后重试。Uptime Kuma 原生接口没有跨客户端原子版本控制，因此其他仪表盘仍可能在校验后的极短窗口内修改同一项。
- 验证配置和远端写入创建后台任务，页面通过 Query 读取进度，日志中心保留结构化任务结果；任务创建审计与执行结果分开记录。连接中断后先核对远端状态及任务结果，不自动重试新增、修改和删除。断开接入只清除本地配置及凭据，不删除远端监控项。

接入层针对 Uptime Kuma 1.23/2.x 原生事件契约实现，测试使用隔离 HTTP/WebSocket 服务和临时数据库，不连接生产实例。Prometheus 文本解析使用 Apache-2.0 许可的 `prometheus/common/expfmt`，Socket.IO 的有限事件适配复用已有 Go WebSocket 库，不引入额外业务运行时。

## 调度与告警事实模型

控制面策略是调度参数的唯一配置来源。健康样本先生成账号健康评估，再由调度引擎生成目标，完全模式才允许自动执行远程变更：

```text
health_samples -> account_health_evaluations -> routing_decisions -> routing.writeback
                                                              -> operation_audit
```

- `routing_decisions`：本轮调度判定和期望状态，不代表已经在 Sub2API 生效。
- `accounts.routing_state`：远端读回一致后确认的当前生效状态；仅计算字段不得改写它。
- `operation_audit`：远程写入、读回和本地提交的执行事实，用于执行失败告警与日志。
- 调度异常告警读取 `routing_decisions`，文案统一称为“调度判定”；自动执行失败告警读取 `operation_audit`。
- 上游余额同步成功后立即评估并投递该 Host 的余额告警或恢复通知，不等待其他上游、探活、调度计算或写回完成；手动同步和鉴权恢复后的余额同步走同一流程。通知沿用告警策略、恢复开关和去重规则，投递失败保留记录并由后续告警评估重试。充值仍需等下一次成功读取余额才能被发现，通知正文时间表示告警评估时间，不是充值时间；可结合 `upstream.sync`、`upstream.balance_alert` 运行事件与投递记录排查延迟。
- 监控模式只评估健康状态；完全模式保存调度目标并按字段开关自动执行。
- 人工优先位账号不参与自动成本墙、熔断和调权；账号与分组详情显示“人工优先位”，不沿用历史自动处置或待执行目标。真实暂停、平台停用和上游错误仍正常展示，历史健康样本保留供查看。
- 主动探测总开关只读取 `probe.enabled`；`health.source` 只决定常规健康证据来自真实流量还是主动探测。
- 已手动熔断的账号可显式执行单账号、批量或平台模型探活，用于诊断上游并记录结果；探活不会解除熔断或开启调度。自动巡检及恢复探测仍跳过手动熔断账号。任务排队后新增的手动熔断或人工优先位仍在执行前复核并跳过。
- 调度策略「巡检与采样」支持每日自动探活暂停时段（`probe.pause_window`），默认关闭；启用后配置开始时间、结束时间与 IANA 时区，默认北京时间 `00:00–08:00`。支持 `23:00–08:00` 等跨午夜时段，包含开始时间、不包含结束时间。暂停覆盖常规自动探活、真实流量不足时的回退探活及恢复探测，结束后由下一轮巡检自动恢复；排队请求和重试在发出前重新校验，已发出的请求允许完成。暂停不生成健康成功或失败证据，不影响真实流量采集、调度及显式手动探活。

账号主动探活由 Console Go 后端直接请求账号上游的生成接口，手动、批量、平台模型探活及自动巡检均不再调用 Sub2API 的账号测试接口。执行前通过管理 API 按稳定账号 ID 只读获取当前 Base URL、协议和模型映射。模型映射按 Sub2API 的精确匹配优先、末尾 `*` 最长前缀匹配规则解析（包括 `*` 兜底），未命中时保留请求模型；`[1m]` 等字面后缀不会被当作正则规则。仅校验本次实际命中映射的上游目标是否为具体模型名；其他规则的目标含通配符不会阻断本次探活，命中的目标仍含通配符时明确跳过，不推测替换或递归映射。管理接口隐藏 API Key 时，按账号的稳定上游 Host、Key ID、分组 ID 读取 Console 私有凭据库中固化的 Key；本地缺失或只有遮罩值时，使用已有上游鉴权读取同一绑定 Key，重新核对账号绑定与 Base URL 后持久保存，再执行探活。固化的 Key 不设置缓存有效期，后续探活及服务重启后直接从私有凭据库读取，无需重复向上游获取；保存失败会明确跳过，不写健康失败证据。有有效绑定及上游鉴权时，无需手动补填 Key；缺少绑定或绑定不唯一时明确跳过。兼容管理接口直接返回有效 Key 的版本，但不调用账号备份导出接口获取凭据。凭据仅由 Go 后端读取和保存，不返回浏览器或写入任务结果。手动和自动探针使用策略中的 `probe.prompt`（默认 `hi`），请求不附加 system 或 instructions 提示词。上游服务自身如何处理提示词仍取决于上游。

当前支持 API Key 账号的 OpenAI Responses、Anthropic Messages、Gemini GenerateContent，以及智谱/Kimi/DeepSeek/Grok 的 Chat Completions；明确配置 `api_protocol`、`api_base_urls` 时按配置选择。OAuth、配置代理、无效模型映射、缺少凭据或管理详情读取失败会显示跳过原因，不生成健康失败证据，也不退回测试接口。直连请求禁止重定向和隐式切换 Host 或协议，保留已配置的有限重试；只有实际文本到达才判为通过，元数据、思考或工具参数不算回复，HTTP 200 中的业务错误也按失败处理。首字计时从上游生成请求开始，不包含管理详情读取；上游忽略流式请求而返回完整 JSON 时，可按文本判定通过，但不记录首字延迟。自动巡检保留无法执行的账号及原因；直连结果表示该账号上游凭据与模型接口的可用性，不验证 Sub2API 的转发和调度链路。

真实请求从 `GET /api/v1/admin/ops/requests` 采集结果与错误，并通过 `GET /api/v1/admin/usage` 按账号 ID、请求 ID 补充成功请求的 `first_token_ms`。总耗时与首字分开保存；使用记录接口失败时保留运维证据并报告首字采集失败，后续重试可以为已有样本补齐首字。

`Our servers are currently overloaded`、`The service is busy` 和模型 `at capacity` 等满载错误按临时网关失败计分，不归入余额耗尽或凭据失效。HTTP 200 的流式响应中出现 `response.failed` 同样视为失败；主动探活保留内层错误状态码，没有状态码但明确表示满载时按 503 处理，只有配置允许时才进行有限重试。反复满载沿用异常确认、健康降级及网关错误处置，不直接删除账号。控制台只调整后续请求的账号调度；正在转发的请求由 Sub2API 网关负责输出前重试或切换账号，已经输出文本或工具调用后不能透明重放。

巡检采集错误会反映在任务状态中：数据源全部失败且没有可用缓存或探活证据时标记失败并停止本轮健康计算和写回；仍有可用来源或缓存时继续执行并标记部分失败。正常空流量、已关闭探活或探活暂停不自行产生失败。

真实请求首字和主动探针测得的首个内容到达时间，都按健康分公式中的 `scoring.slow_ttfb_ms` 判断慢响应；默认严格超过 5000ms 时，单次按配置的响应慢分值（默认 65 分）参与短期、长期和综合评分。延迟处置使用独立的 `breaker.latency_ttfb_ms` 和次数窗口。当前状态、连续失败及恢复条件使用新鲜证据：真实流量按 `traffic.lookback_minutes`，探针按独立的 `probe.freshness_seconds`（默认 900 秒），不再随全局或分组探测间隔变化。短期、长期和综合评分按独立的 `scoring.history_window_minutes`（默认 1440 分钟，最多 7 天）回溯，再受短期 10 条、长期 60 条的数量窗口限制。有新鲜流量时使用流量历史及比最新流量更新的探针，否则使用探针历史；没有新鲜有效证据时不启用历史评分，不能凭旧成功记录确认当前健康或恢复。熔断账号沿用新鲜恢复样本评分，避免熔断前历史阻碍恢复。可在调度策略的「巡检与采样」及「健康分公式」中分别调整；历史回溯不会补抓或生成未保留的样本。展示的 P50/P95 及常规性能权重只使用真实请求首字，不混入探针或请求总耗时；排位晋升的独立探针比较见下文。页面显示有效样本数，正常成功探针标为“探测通过”。账号管理的健康评分详情分别展示本轮短期、长期实际样本数；短期样本是长期样本中最新的一部分，不重复相加。短期数量与同轮评分绑定，旧评估缺少记录时显示“未记录”，下一轮调度后补齐。设置中的“评分历史范围”和“当前探针有效期”表示时间范围，不是样本数量。

评分历史范围内没有有效评分样本时，回退到仍在当前有效期内的证据，不将新鲜证据显示为零样本。熔断、连续异常确认、恢复和自动处置分别按各自所需的数量窗口读取证据，缩短评分窗口不会截断这些规则；性能统计仍使用原评分数量窗口。存在已记录的熔断起点时，恢复仅接受严格晚于该起点的样本，熔断前的成功流量和探针不能使账号重新接流量。

高频流量的健康保持时长按保持区间内的真实请求核对，不受评分条数或健康缓存条数限制；期间的失败、中性错误和疑似空回复仍会阻断连续恢复。调度分为零是有效结果，不回退到历史展示分。多个账号同时待熔断时，保底计算会纳入本轮尚未处置的候选，优先移除致命及低分账号。

账号管理打开时，当前页账号的真实流量由独立采集通道检查，成功采集后间隔约 5 秒继续检查，不等待巡检中的主动探针。重复查看同一账号共享采集，最多并发 4 个账号；离开页面或翻页后取消不再观看的采集。失败后间隔 30 秒重试。实际刷新延迟还受上游日志可见时间、接口耗时和并发排队影响。

自动巡检的主动探测按账号分批执行，每轮最多选择 `probe.concurrency × 8` 个到期账号，兼顾单轮调度响应与全量覆盖速度，优先从未探测或上次探测时间最早的账号。「持续评估候选速度」（`probe.performance_exploration_enabled`）默认开启，在用账号也按既有探测间隔提供性能参考，会增加探测请求；关闭后保留「有新鲜流量时跳过探测」的原有行为。该开关不绕过主动探测总开关、分组设置、暂停时段、成本墙、人工保护或批次并发限制。其余到期账号留待后续巡检，不生成探测失败或成功证据，任务详情记录待检数量。每个选中账号仍检测其配置的模型，手动巡检不受该批量限制。每批完成后即继续健康计算和调度写回，避免数百个账号的慢响应阻塞整轮；单轮耗时仍受上游请求、探测超时和调度写回影响。心跳间隔从上一轮结束后计算，不是整轮的耗时上限。价格分组调整没有需要修改的账号时直接返回，不等待探测持有的管理目标变更锁。账号倍率的只读采集固定管理目标快照但不占用全局变更锁，保存观测及写入前仍重新校验目标、绑定与人工保护状态。

账号排位以已生效的远端优先级为起点。普通晋升要求足够的有效成功证据（`weights.performance_min_samples`，默认 5），综合收益超过变更阈值（默认 10%），且相关账号不在写入冷却中；可以越过差异很小的中间账号，但不会跨越对其明确更优的账号，避免价格、速度和健康取舍形成循环换位。已确认降级或不可用账号及时让位。新增或退出成员不再整体平移其他账号的优先级，共享并发容量紧张时也沿用稳定比较规则。

排位比较优先使用双方同模型且足量的真实请求首字。缺少这类数据时，持续速度评估可使用双方同请求模型、实际模型、协议和请求指纹的独立探针序列；至少达到上述样本数，最新探针须在当前有效期内，历史部分受评分回溯范围限制。重试恢复、缺失实际模型、未测得流式首字、配置变化或失败会中断性能序列。探针比较的速度比值最多按 2 倍计算，且不超过已配置的速度优势上限；不同模型或工作负载不制造速度优势。界面 P50/P95 仍只统计真实流量，探针不会混入这些数值。流量和探针分别最多保留每账号 200 条，防止高流量挤掉低频参考探针；晋升取样数量至少覆盖最低样本门槛，展示统计仍沿用评分数量窗口。

账号列表、详情与需要会话鉴权的 SSE 使用后端当前证据评分，复用调度的样本选择、评分窗口及熔断恢复证据规则；同一只读数据库快照同时读取评分与最近结果，前端一起更新健康分、样本数、首字延迟和色块，迟到的旧实时快照或列表响应不得覆盖更新的健康数据。评分详情展示快照评估时间与最新证据时间。该读取只计算展示值，不修改已保存的调度评估、状态、权重或上游配置；调度执行仍由原巡检流程负责。

最近结果以稳定 ID 去重，补充首字延迟时原位更新；色块从左到右由旧到新，仅显示最近 10 条，快照最多返回 100 条，浏览器仅在 React Query 内存中保存有界结果。页面显示连接和采集重试状态。被归类为客户端请求错误的中立结果使用中立色，明确不计入健康评分，不显示零分；真实网关错误和致命错误仍按各自类别与分值展示。

真实流量中，成功请求明确记录 `input_tokens=0` 且 `output_tokens=0`，并且没有缓存读取、缓存写入或图片产出时，标为“疑似空回复”（`empty_response`）。单条按 `scoring.event_scores.empty_response`（默认 40 分，可在事件分值表调整）参与现有健康评分，不是直接从账号总分扣 40 分。这类请求计入失败与异常确认，不计入恢复成功次数及成功请求速度统计；偶发先温和降权，连续或窗口内反复出现按现有确认规则加重降级，不因双零直接认定凭据失效。用量按账号 ID 和请求 ID 关联，晚到用量更新原样本，缺失或无效字段不补零；后续非零用量可纠正判定。Token 双零属于异常信号，不能证明响应正文为空，未上报双零的空正文不在此规则覆盖范围内。

启用健康降级后，有效健康分严格低于 `degrade.score_threshold` 即判定降级，不再要求先达到熔断层的失败或慢响应次数。短暂失败尚未达到确认阈值时，判定携带 `evidence_pending`，按半幅健康门控损失温和降权，不额外叠加降级优先级步长、负载折扣或并发伸缩。待确认调度分为 `min(上一调度分, (100 + max(weights.gate_floor, 当前健康分)) / 2)`；重复评估相同样本不会累计减分。例如门控底线 40、上一调度分 100、当前健康分 40 时，展示的健康分仍为 40、状态判定为降级，调度分暂用 70。权重最终仍按组内预算归一化，并受现有写入死区和冷却控制。

连续失败或滚动窗口达到现有确认阈值后，使用完整健康分及降级处置；已确认的降级不会因失败次数暂时减少而退回温和处置。中性客户端错误保留之前的调度判定，人工控制、致命错误、熔断保底、成本墙及连续成功、健康保持、恢复冷却规则继续优先执行。健康分恢复到 100 也不代表恢复条件已经全部满足。

调度策略的「成本墙」提供「启用成本墙拦截」「无可用账号时允许保底」「拦截期间停止自动探活」三个开关，分别对应 `cost_wall.enabled`、`cost_wall.fallback_enabled`、`cost_wall.stop_auto_probe`，默认均开启。关闭总开关后恢复正常调度评估并解除成本墙的自动探活限制，保留两个子开关的配置；关闭保底开关后，即使没有可用账号也不启用成本墙账号；关闭停止自动探活开关后，拦截账号仍按常规探活规则执行。调度写入仍遵守运行模式与自动执行开关。

成本墙使用包含利润率和安全缓冲后的有效阈值：默认情况下，账号倍率等于或超过所有受管分组的成本墙时，关闭调度并停止自动探活；手动探活仍可用于诊断。仅当分组没有可用账号时，才按倍率、健康分和稳定 ID 选择一个符合安全条件的成本墙账号临时保底，正常账号恢复后再次关闭。保底启用确认后可以恢复自动探活；仅有未执行的保底目标不会触发探活。局部重算也核对同组范围外的现有可用账号；多分组账号只要仍有受管分组低于成本墙，就保留账号级调度。人工暂停、停用、绑定失效及上游禁止接流量等保护不因成本保底而解除。

账号设置提供默认关闭的「无视成本墙」开关，切换后立即独立保存。开启后，该账号所有分组的成本墙调度拦截、权重置零和自动探活拦截均被豁免；关闭后恢复常规成本墙判断。配置按稳定账号 ID 保存在 Console 策略的 `scope.ignore_cost_wall_account_ids` 中，上游同步不会覆盖，删除账号时清理。切换只更新本地配置，后续调度与探活使用新配置；不会直接开启远端调度，也不会解除人工暂停、熔断、并发限制、绑定失效或其他安全保护。正常价格排序和健康评分仍然有效，已计算的旧策略目标需重新核对后才能写入。

自动写回在取得变更租约后及批次实际提交前重新核对运行模式与完整策略，自动删除也在执行前复核；排队或读取远端期间发生策略变化时，旧目标必须重新计算。确认因策略或运行模式变化而未执行的操作记录为跳过，保留原因，由后续调度重新计算，不产生自动处理失败或恢复通知；配置读取、远端写入和写后复核失败仍正常告警，跳过不能清除此前真实失败。关闭「接管全部账号」后，写入前会将最新远端值与托管基线比较，检测到外部修改时保留当前值并交还控制权；该交还状态持续保护账号，后续旧目标及自动恢复基线不能重新接管。

调度目标携带计算时策略指纹，计算后修改策略会使旧目标失效；取得发送并发槽以及每次远端写入重试前再次校验授权。关闭写后验证也会为明确成功的实际字段写入启动冷却，但容量释放和恢复仍要求读回确认。交还控制权只有在全部恢复步骤成功后才删除基线，部分失败保留原始恢复依据和已确认的进度。

## 上游共享并发

手动同步上游或余额后，同步任务会使用最新额度及完整账号库存重新计算调度；任务完成后刷新账号与分组展示，无需手动触发计算。计算失败会在同步任务中说明，已同步的额度仍保留。监控模式只更新健康评估；完全模式保存调度目标，实际分配和恢复由后续巡检核对最新容量后执行。

Sub2API 上游的「同步上游」和「同步余额」会从用户资料接口 `/api/v1/user/profile` 同步 `concurrency`。该值是用户共享上限，不是每个 Key 或账号各自独享的额度。正数表示有限额度，`0` 按 Sub2API 协议表示不限流；未返回字段显示「未读取」，同步失败或上游配置、鉴权变更后保留上次确认的额度并标记缓存状态，需要重新同步。同步确认用户身份改变后不沿用旧用户的额度。浏览器只接收额度与状态，不接收用户凭据。

账号添加的并发留空时，由 Go 后端按稳定上游 ID 平分本批新账号的剩余额度，并在确认弹窗展示实际分配；有余数时按提交顺序分配，单账号至少为 1。剩余额度不足以给本批自动分配的账号各分配 1 时，允许以并发 1 保持停用并添加为「等待并发额度」，确认弹窗说明该状态；后台确认远端停用后才记录等待状态，不预留容量。确认提交保留等待状态，恢复仍须由调度器核对最新容量、健康、运行模式及写入开关。要求立即启用的新增账号仍拒绝超额创建。已有账号（包括人工暂停、无分组账号）先保留配置容量，只有已确认的「等待并发额度」暂停释放预留；更新已有绑定不占新增名额。手动填写先预留并校验整个批次总量，不得超过用户剩余额度。额度未知或失效时先同步，明确不限流及非 Sub2API 上游使用账号创建默认值。新增前持有容量租约并读回已有账号的远端并发，额度变化导致不足时停止新增并提示重新分配，不改写已有账号来腾挪容量。

即使关闭智能扩容，恢复目标也要求已确认的上游额度；未知或缓存失效时保持暂停并记录原因。运行中账号缺失当前并发时先同步，不生成无法通过容量复核的写入；真实读取或写入失败仍保留告警。

Sub2API 分组倍率同步同时读取鉴权用户的 `/api/v1/groups/rates`，按稳定分组 ID 使用专属倍率覆盖基础倍率，再应用充值比例换算；专属倍率不是叠乘折扣，零倍率也须保留。接口返回空映射或 `data: null` 表示没有专属倍率；旧版本仅在 HTTP 404 时回退基础倍率。鉴权失败、服务异常或返回格式无效时同步失败并保留已有倍率，禁止静默覆盖为基础倍率。

「上游共享并发分配」是 Sub2API 专用开关（`upstream_concurrency.enabled`，默认关闭，沿用原独立下调开关）。完全模式下，按稳定上游 ID 汇总共享额度，先为受管且符合健康条件的每个账号分配至少 1 个并发，再按调度权重分配剩余额度；只有可用额度少于账号数时才让低优先级账号等待。支持全部账号、指定账号和指定上游三种范围（`upstream_concurrency.account_mode=all|selected|upstreams`，`account_ids` 使用稳定账号 ID，`upstream_ids` 使用稳定上游 ID），旧配置默认全部；指定范围为空时不启用任何账号。指定账号时新账号须手动选入；指定上游时所选上游下新添加的健康账号自动参与，别名 Host 不重复计算。范围仅限制本功能，智能扩容仍按其配置独立执行；未选账号保留容量，不得通过旧分配任务越过新范围写入。智能扩容关闭时，只按各 Sub2API 上游真实额度分配，不启用 scaling 中的全局上限、单账号上下限、步长、冷却或通用写入开关；New API 不受该共享额度机制限制。全局或分组开启智能扩容时，同时遵守全局上限，对开启扩容的账号使用配置的单账号上下限、步长、冷却和自动执行开关。手动、熔断和范围外账号保留容量；范围内由控制台确认停用的成本拦截账号释放预留，但不会因此自动恢复。占用过多的账号先缩减，读回确认后再扩大其他账号或恢复已确认的「等待并发额度」账号；未确认的缩减不会提前释放容量。恢复前必要时先调整暂停账号的正数并发，下一轮确认后恢复，不恢复人工暂停。额度未知时不扩容，有限缓存仅用于下调；上游 `0` 表示不限流，不据此写入账号零并发。写入前再次核对模式、策略、稳定归属、实时账号快照及上下游容量，其他字段仍遵守原有自动执行开关。监控模式只预览。

需要双向分配和自动恢复时，启用调度策略中的「智能扩容」及「并发上限」「调度状态」自动执行开关。同一稳定上游 ID 下的账号按现有调度权重分配整数并发；价格优先、速度优先、均衡与稳定性策略及分组覆盖继续决定权重。两种方式均对跨分组账号去重，同一上游的别名 Host 共用额度；手动管理、暂停、排除及本次范围外账号保留容量，没有分组的账号也计入容量核对。未知上限不自动增加并发，上限为不限流时继续受 Console 全局预算约束。

智能扩容中，额度不足以给每个候选账号至少分配 1 时，策略排序靠后的账号进入「等待并发额度」，关闭可调度状态；不会写入表示不限流的 `0`。容量恢复后重新评估健康和调度条件，先确认账号并发配置，再恢复调度。暂停账号的原配置并发超过全局可用容量时，先缩至可用的正整数并发，读回后再评估恢复；没有余量时继续等待。任何恢复操作若同时调整并发，必须先读回确认并发再启用账号，参数写入失败或读回不一致时保持暂停。缩容、暂停尚未读回确认的容量不会被用于扩容，账号并发配置仍受全局上限、单账号上下限、步长和冷却控制。智能扩容写入需要完全模式及两个自动执行开关；缺少必要开关时保留预览并提示补全配置，阻止部分写入。缓存额度只允许缩减，不用于扩容或恢复。

并发写回会获取同一上游关联账号的变更租约；启用智能扩容时还锁定全局账号库存。取得租约后重新核对稳定 ID 归属、最新已同步额度及远端账号容量，在同一批次内同时校验全局与上游预算，再统一预留增长额度。只有已确认的「等待并发额度」暂停释放保留量，人工暂停等其他暂停仍保留配置并发。自动交还控制权时恢复原并发或调度状态，也须经过容量检查。开户与并发写回共用容量租约，避免快照读取后并行创建账号占用余量。

写入前其他任务或人工操作已用掉的容量不会再次分配；远端快照缺项、包含尚未同步的账号、读取失败、身份变化或超限会阻止扩容与恢复，并给出重新同步或计算的提示。服务器之外直接发往同一 Sub2API 用户的请求仍共享上游限额，控制台不能为未关联的外部消费者预留实时槽位，也不能锁住绕过 Console 直接修改账号的外部操作。

上游列表的「已配置」统计当前可调度账号的配置并发之和，「目标」包含最新调度目标；这些值不是实时请求数，含未知或不限流账号时不显示虚假的有限合计。分组分配中的并发在本轮没有调整目标时沿用已确认配置，暂停账号的调度容量为 0；任一参与账号容量未知或不限流时，总量显示为未确认。本功能约束用户总额度；Sub2API 另外设置的分组用户并发上限仍由上游执行。

## 成本流量告警

告警策略中的「无利润／亏损流量」默认开启：最近 5 分钟内采集到真实请求，且当前已同步的账号倍率大于或等于请求所属分组倍率时，按账号与分组分别告警。比较使用精确十进制，包含等倍率，不以探活、可调度状态或主分组推断真实调用。采集时保留请求的稳定分组 ID；运维请求缺失分组时，仅按同一账号 ID 与请求 ID 从用量记录补齐，不能确认分组的记录不参与此项告警。

通知包含当前两端倍率、窗口内已采集的去重请求数和最近调用时间；采集受流量样本上限约束，请求数不代表完整账单。这是当前倍率下的成本风险提示，不重建历史计费，也不直接修改账号调度。倍率降低或窗口内不再检测到符合条件的请求时解除告警；倍率缺失、无效或绑定无法核对时关闭旧告警并说明证据不足，不发送恢复通知。「成本流量告警解除」可单独选择发送，默认关闭，并沿用重复提醒、冷却及合并策略。

共享并发容量暂不足时，扩容或恢复记录为「等待并发额度」并跳过本轮写入，不计入自动执行失败，也不发送失败或恢复通知；后续调度继续复核，容量释放并确认且仍满足调度条件时再执行。任务结果与审计保留用户上限、已分配及预留容量、剩余额度、本次新增需求和账号调整前后调度容量。暂停账号的当前调度容量为 0，不代表其配置并发为 0，这些值也不是实时请求数。旧版误记为执行失败的容量等待告警停止排队，并在下次告警评估时直接关闭，保留历史记录。远端接口失败、快照缺失、状态无法确认及真实写入失败仍按异常处理，容量等待不会清除此前未解决的真实失败。

## 模型参考价格

价格分组调整在每个已加入的互换组内，优先选择满足目标成本利润率（利润 ÷ 账号成本）且售价最低的分组。每个分组可单独设置“最低迁入倍率”，仅账号成本倍率大于或等于该值时才参与该分组的价格选择；留空表示不限制。低于当前分组最低迁入倍率的账号会重新按价格选择本互换组内的其他合适分组。若符合最低迁入倍率的候选分组均未达到盈利目标，则回退到同平台、售价最高且能够覆盖成本的分组，并提示利润未达标；没有符合最低迁入倍率且能覆盖成本的可用分组时保留原分组，并记录原因。相同售价按稳定分组 ID 选择，不跨互换组迁移。例如目标为 25%、账号成本为 0.21、平价组售价为 0.20、旗舰组售价为 0.25，且未设置最低迁入倍率时，迁入旗舰组，实际成本利润率约为 19.05%。自动巡检完成价格分组调整后，再按新成员关系计算成本墙与健康状态；分组迁移不绕过人工保护、熔断或分组利润控制。

New API 渠道管理使用可搜索、独立滚动的渠道表格，复用全局工具栏、空状态及分页，支持切换每页行数和跳转页码，支持多选、全选当前筛选结果及跨页保留选择（每次最多 50 个）。新增渠道通过弹窗按需读取配置。单个渠道按稳定 ID 上架或下架指定模型；多渠道操作预览每个渠道的影响范围后创建后台任务，逐项执行并保存成功、失败和未执行结果，关闭弹窗不打断任务。操作先预览变更范围，确认后核对渠道版本，仅更新模型列表并读取远端结果；失败不自动重试，需刷新列表核对。由于 New API 更新接口忽略空模型列表，下架时至少保留一个模型；需要全部停止服务时，应在 New API 停用渠道。

系统设置中的菜单显隐保存在控制台后端。首次使用时导入当前浏览器已有偏好，之后刷新、重新登录及更换浏览器均使用后端设置；可以继续修改或恢复默认。系统设置入口始终显示，隐藏菜单不限制通过地址访问页面。

New API 模型价格页对 DeepSeek、Kimi（含 Moonshot 名称）、MiniMax、GLM、Qwen 家族采用官方来源。Go 后端分别读取 [DeepSeek 中文定价](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)、[Kimi 模型推理定价](https://platform.kimi.com/docs/pricing/chat)、[MiniMax 按量计费](https://platform.minimax.cn/docs/guides/pricing-paygo)、[GLM API 定价](https://docs.bigmodel.cn/cn/guide/start/pricing) 和 [Qwen 百炼定价](https://help.aliyun.com/zh/model-studio/model-pricing)。只采用官网明确列出的模型 ID、大小写变体和明确公布的兼容别名，不推测日期版本或渠道前缀；未列出或尚不支持计价单位的型号标为缺失，不再套用第三方旧价。其他厂商仍读取公开远程价卡，缺失时通过 Sub2API 管理接口获取默认价格。所有价格保留来源数值，不做币种换算；每 Token 与每百万 Token 仅按计价单位换算。

DeepSeek 分别保留峰谷输入、输出、缓存读取价格，以及北京时间工作日的半开时段 `[开始, 结束)`。Kimi 直接读取官方合并后的模型推理定价表；MiniMax 直接访问当前官方域名，采用标准服务当前价（不含 `priority` 优先服务）；GLM 保留输入长度及输出长度阶梯；Qwen 采用华北 2（北京）实时 Token 价格及页面标明的折扣，保留上下文与思考/非思考档位，思考档以请求的 `enable_thinking=true` 匹配。Qwen 的缓存折扣需另行配置，不从正文提及的“享有折扣”推测单价；音频、图像等不同计费单位不会按文本 Token 误读。

参考价格表展示来源链接、适用范围和各档价格。单项和批量同步使用完整 `tiered_expr`，由 New API 计费端选择档位；目标需支持 `tier`、`len`、`c`，分时价格另需 `hour`、`minute`、`weekday`，思考模式分档另需 `param`。控制台不定时覆盖静态价格。同步时先保存新旧表达式的并集，再切换计费模式，最后清理已停用表达式；失败按各步骤的前置状态逆序恢复，避免 New API 校验到已启用阶梯但缺少表达式的中间状态。公开官方页面允许同一 HTTPS 站点内有限次数的规范网址跳转，管理 API 仍禁止跳转，管理凭据不发送至公开页面。

价格缓存在本机配置库，远程价卡与 Sub2API 默认价有效期 24 小时，官方价按厂商独立缓存 1 小时，重启后仍可复用。多个厂商并发刷新，平台目录和远程价卡查询也并发并分别限时；缓存按管理目标隔离。“强制刷新参考价格”绕过缓存重新获取。官方请求或解析失败时仅保留上次成功的官方价格并显示具体原因，首次失败则不提供该厂商的替代旧价；其他厂商成功结果正常保存。页面格式变更不会被当成取消阶梯或分时价格。管理密钥不会发送到浏览器。

价格比对读取 Sub2API 上游的模型广场；仅在接口返回 HTTP 404 时，使用原上游登录身份尝试 `/api/v1/channels/available`，成功后在选择项标明“渠道价卡”。该兼容来源使用上游渠道公布的基础价格，不叠加分组或个人倍率，不作为官方参考价；仅比较可明确表达的固定 Token 单价和按次价格，同名模型多渠道异价、阶梯价及图片计价不压成单一价格。两个接口都不可用时保留具体原因，其他可用上游仍可比对。HTTP 401 需要先恢复该上游鉴权再刷新，HTTP 403 需要检查访问权限；不会因鉴权失败切换成匿名身份。

模型价格页支持跨页勾选和全选筛选结果，每批最多同步 1000 个模型。批量同步先展示目标价格和跳过原因，确认后一次提交有效模型，并逐项核对读回结果。比较 Sub2API 默认价格时，未配置的缓存写入、1 小时缓存写入和图片输入与对应默认零值不产生差异；明确的非零价格差异以及输入、输出和缓存读取的零价仍正常比较。

比较、批量预览、单项同步和远程价格列表共用前端查询缓存，按后端返回的到期时间判定是否需要重新读取；读取旧缓存不会延长其有效期。主动“强制刷新参考价格”仍立即请求后端更新。后台刷新保留已有价格、比较结果和分页，仅更新刷新按钮状态；参考价过期或读取失败时不能用旧数据执行批量同步。模型检测、渠道模型选择和无绑定 Key 扫描同样保留刷新前的列表与选择，并在刷新中或失败时禁用依赖新结果的写入操作。

## 常规模型检测

账号管理提供页面级与账号行的“模型检测”入口；账号行按稳定 ID 跳转并预选账号，检测完成后刷新账号管理的结果和统计。单选账号可查看上次检测结果，并返回账号管理。

账号置信度和稳定性分别显示短期 24 小时、长期 30 天窗口。置信度采用常规行为检测一致率的 95% Wilson 下界，每个账号与模型组合算一个样本，多轮请求不重复算样本；少量通过不会显示为 100%，不代表模型身份的真实概率。不同模型与规则版本合并统计，无法判定或请求失败单独列为无结论，不计入分母。统计读取保留的常规检测历史，不受最近 100 个任务限制；清理任务历史后覆盖范围可能缩短。动画和前置检测不计入置信度。

稳定性是已采集真实请求与主动探活的成功率，按稳定账号、来源、证据 ID 去重，跨分组不重复累计；明确零用量的疑似空回复计为失败，用量补齐修正原样本。后端自采集时起独立保留 30 天精简结果，健康评分仍只使用原有评分窗口。没有有效样本显示“暂无样本”，悬浮或键盘聚焦可查看通过、失败、无结论数量与统计时间；这两个展示指标不改变调度、熔断或健康分规则。

OpenAI OAuth 账号可直接在“常规检测”中选择，支持 Sol 画像与 Astra 多轮检测，无需绑定 API Key。Go 后端按稳定账号 ID 从创建任务时的管理目标读取当前 Access Token 和工作区，仅在执行内存中使用，并请求固定官方 Codex Responses 接口；不会刷新授权、修改线上账号或写入健康证据。任务保留创建时的检测规则版本，排队后管理目标、账号类型或平台变化时停止执行。授权缺失或失效需先在账号工作台恢复；配置了出站代理的账号暂不支持此入口，不会自动绕过代理。

“检测规则与题库”默认展示当前生效版本，按 Claude、GPT 列出支持的模型，并提供题目搜索、分页、答案特征、评分权重与中文判定条件。GPT 的首轮题目、补充题目及两阶段阈值分别展示。检测依据固定题目的回答特征进行比较，结果不是模型身份认证，也不代表答题正确率；常规检测仅可选择已有规则且所选账号共同提供的模型。

`gpt-6-astra` 使用独立内置题库，每轮分别请求糖果题（答案 `21`）、知识截止日期题（明确无法提供日期且不回答日期）以及 low、mid 两档 juice 题。前两题使用 low；mid 在接口中发送为 `medium`，不请求 high、xhigh 或 max。订阅特征为 low `2`、mid `4`，官 Key 特征为 low `4`、mid `10`；两档或多轮结果冲突、格式不符、请求失败时不推断来源。题目匹配与来源特征分别展示，仅作为行为参考。Astra 规则随程序发布，在题库中只读展示，不参与 Claude/Sol 的 JSON 草稿编辑；检测结果另行记录内置规则版本与指纹。

JSON 编辑、版本说明、保存草稿、发布和历史版本恢复位于“高级设置”。保存草稿不会改变当前生效规则，可切换到草稿预览；未保存的修改须先保存，之后确认发布才会影响新建任务。已排队或运行中的任务继续使用创建时的规则版本。

## 模型动画检测

OpenAI OAuth 账号同样支持动画检测、前置检测及两者组合，也可明确启用定时检测，无需绑定 API Key。任务按稳定账号 ID 读取当前授权，固定使用官方 Codex Responses 接口，不受常规行为画像模型列表限制；前置检测保留题目选择，Astra 使用 low 思考等级，动画结果仍须通过 SVG 安全校验后以隔离图片展示。取消任务会停止后续题目及动画阶段；授权失效、账号或管理目标变化、配置了出站代理时返回明确失败原因，不自动刷新授权或绕过代理。

动画检测内提供“前置检测”，可单选糖果题（答案 `21`）、知识截止日期题（明确无法提供日期且不回答任何日期）或全选，默认全选，不请求 juice。账号与自定义接口均可手动执行；`gpt-6-astra` 使用 low 思考等级。结果只展示和判定本次选中的题目，区分通过、不通过、无法判定或请求失败。账号可按当前模型、题目选择和筛选范围“选择通过”或“选择不通过”（最多 20 个）后继续确认动画生成；题目范围不同、无法判定、请求失败和执行中的账号不自动选入，开始新一轮前置检测后不沿用旧的通过结果。

账号“自动检测设置”可选择定时执行动画检测或前置检测，前置检测同样支持单选或全选题目，并保存题目范围供后续执行及重启恢复；未指定题目的配置默认检测两题。自动检测默认关闭，间隔为 1～1440 分钟；每个账号保存一套定时内容，前置检测完成后不自动触发动画生成。定时任务由 Go 后端执行，复用账号互斥、最多 3 个并发、取消和历史记录机制。前置检测结果不修改行为画像或调度健康证据，自定义接口不支持定时执行。

“模型检测”页面提供“常规检测”和“动画检测”两个 Tab，切换时保留各自选择。动画检测选择 1～20 个账号，顶部统一设置模型，支持关键词、分组、平台和人工优先状态组合筛选。模型 ID 可手动输入，也可点击“获取模型”读取已选账号共同支持的模型；列表读取失败时保留已填模型，手动输入不依赖模型列表。开始前会展示账号、稳定 ID 和模型供确认。账号默认每页展示 12 个，可调整为 6 或 24 个；翻页和搜索会保留已选账号及填写的模型，“选择前 20 个账号”作用于全部搜索结果。

Go 后端使用账号绑定的 Key 发起固定的“鹈鹕骑自行车”SVG 生成请求，支持 OpenAI Responses、接口明确不支持时回退 Chat Completions，以及 Anthropic Messages；请求启用流式返回，后端逐事件接收，收到协议完成事件后结束读取，不等待上游关闭连接。OAuth 动画与自定义接口使用相同的完成规则，仍兼容上游返回完整 JSON；生成全过程受页面设置的请求总超时限制，不完整结果不会展示为成功动画。全局最多同时生成 3 个动画，同一账号不能重复执行。每个结果包含请求 ID、请求/返回模型、完成时间、耗时和失败原因，可单独重试失败账号，也可取消未结束任务。切换 Tab 或离开页面不取消已创建任务，返回动画检测可查看最近 20 个任务。

动画检测也支持“自定义接口”：无需创建账号，填写 Base URL、API Key、OpenAI / Anthropic 接口类型、模型和超时后，确认目标地址及 API 用量即可生成动画。模型可手动输入，也可点击“获取模型”，由 Go 后端使用当前地址和 Key 读取 `/v1/models`，支持分页、搜索与键盘选择；读取失败时保留手填模型，修改地址、Key 或接口类型时取消旧请求并清除旧列表。模型列表请求和响应均不持久化凭据。Base URL 可带路径及 `/v1`，不得包含用户名、密码、查询参数或片段。自定义检测由 Go 后端执行，复用动画并发限制、取消、历史记录及 SVG 校验；不覆盖账号绑定，不提供自动检测。Key 仅随受鉴权保护的模型列表或任务创建请求提交并在执行内存中使用，不写入任务记录或浏览器持久存储；任务创建成功、清空配置、切换检测来源或离开动画 Tab 时清除输入，后续检测需重新填写 Key。

动画检测会消耗实际 API 用量，只用于观察输出，不修改模型行为画像结论、健康评分、熔断或调度权重。账号检测支持已绑定稳定上游 Key 的 OpenAI / Anthropic 接口账号；人工优先账号可发起常规检测和动画检测，检测不会修改人工优先设置。浏览器只展示后端校验后的 SVG 图片，不执行模型生成的脚本；外部资源、HTML、事件属性和过大内容会被拒绝。

每个账号可独立设置自动检测，默认关闭，间隔为 1～1440 分钟；模型、超时和开关保存在后端配置库。开启前需要确认 API 用量。服务器持续调度，关闭页面后仍会运行；首次开启或服务器重启后等待完整间隔，每次检测结束后重新计时，不补跑停机期间错过的任务。关闭自动检测会停止后续请求，已开始的任务可单独取消。配置保存校验版本并记录审计，生成结果保存在任务记录中。动画结果直接显示在对应账号卡片中，包含动画、失败原因和单账号重试入口；卡片同时显示等待或取消状态。顶部搜索筛选与检测操作各占一行，开始检测位于顶部，分页固定在底部，仅中间卡片区域滚动。任务运行时仅在账号卡片中显示检测状态，顶部开始与取消按钮共用固定位置，不额外插入生成提示或进度区。账号卡片统一高度，自动显示最近 20 次任务中各账号的最新结果，尚无记录时显示“尚未检测”占位及操作引导；SVG 校验支持常见图形属性与经过白名单校验的静态内联样式，仅允许本 SVG 内部资源引用；脚本、事件处理属性、外链与样式表仍会拒绝，属性校验失败会显示具体属性名。动画持续展示，点击可放大预览，支持关闭按钮或 Esc 返回；桌面宽度从 1024px 起每行展示四个账号卡片，卡片以动画为主，模型与完成时间紧凑展示，相同请求与返回模型不重复显示。

## 本地启动

启动 API：

```bash
cd backend
go run ./cmd/server
```

再启动前端：

```bash
cd frontend
bun install
bun run dev
```

打开 <http://localhost:3004>。

前端共享组件、主题尺寸和页面滚动约定见 [界面规范](frontend/STYLE_GUIDE.md)。布局回归覆盖桌面浅色和移动端深色，使用隔离 API fixture，不访问实际业务数据。

运行时不需要安装或挂载 `sub2api-skills`。它只作为业务设计参考；Console 的数据库、任务调度和业务执行都在本项目内完成。

默认数据库均位于当前目录的 `data/`：`sub2api-console.sqlite3`、`tasks.sqlite3` 和 `console-config.sqlite3`。Console 启动和运行不需要任何外部运行库路径，也不会挂载或读取 `sub2api-skills` 的数据。

升级部署前备份数据库。业务库启动时会为兼容旧结构补建缺失表和索引，并在同一事务内校验及记录版本；失败会回滚结构变更，保留原有数据。现有表缺列等不兼容变更需要显式迁移，更新版本数据库不能由旧程序降级打开。新增稳定性统计表从升级后的请求和探活开始累计。

业务库使用 WAL、单连接写入池和独立的只读连接池。倍率同步、巡检、告警等本地写入先在连接池排队，等待支持任务取消；页面查询与只读事务不会占用写入连接。SQLite 的锁等待仍用于处理其他进程的占用，同一数据目录应仅由一份 API 后端提供服务。

首次打开会进入初始化页，需要设置控制台账号密码、Sub2API Admin Base URL 和 Admin Key。远程访问时必须在服务端配置至少 32 个字符的 `SUB2API_CONSOLE_SETUP_TOKEN`，并在初始化页输入相同令牌。令牌只通过 `X-Setup-Token` 请求头发送，不写入配置数据库，初始化完成后即不能再次使用该接口覆盖配置。

首次使用 Docker Compose 时，在项目根目录复制带中文注释的配置模板；已有 `.env` 时直接编辑，不要覆盖：

```bash
cp -n .env.example .env
chmod 600 .env
openssl rand -hex 32
```

将生成的令牌填入 `.env` 的 `SUB2API_CONSOLE_SETUP_TOKEN`，访问端口默认是 `3004`，需要时修改 `SUB2API_CONSOLE_FRONTEND_PORT`。默认配置只有这两项。Docker Compose 自动读取根目录 `.env`，无需逐项 `export`；同名 shell 环境变量会覆盖文件中的值。`.env` 已被 Git 忽略，可提交的 `.env.example` 保持初始化令牌为空。Docker Hub 的 `DOCKERHUB_TOKEN` 继续保存在 GitHub Actions Secret 中。

启动前可以执行 `docker compose config --quiet` 检查配置格式，此命令不会启动容器或发布镜像。直接运行 Go 后端时仍通过进程环境传入配置，不会自动加载此 Compose `.env` 文件。

初始化完成后可在下次重建 API 容器时从部署环境中移除该变量。控制台随后使用 HttpOnly 会话 Cookie 登录；Admin Key 只保存在后端 `data/console-config.sqlite3`，不会返回到浏览器。业务账号、分组、绑定、运行记录和告警只从 Console 自有业务库读取。

单体服务通过同源路径提供页面和 `/api`，远程访问时只需开放 `3004`。多套 Compose 项目可使用不同的 `SUB2API_CONSOLE_FRONTEND_PORT` 并行部署；数据库统一保存在宿主机部署目录的 `./data`，路径无需配置。

使用 Docker Compose 部署：

```bash
docker compose pull
docker compose up -d
docker compose ps
```

默认使用本仓库发布的 `mienvirtuoso/sub2api-console:latest` 多架构单体镜像。镜像地址直接写在 `docker-compose.yml` 中；按版本部署时，将 `image` 标签改为已发布版本。日常本地开发请分别运行前端 Bun/Rsbuild 开发服务和后端 Go 进程；Docker Compose 仅用于部署、镜像构建或容器化验证。

Compose 为单体服务配置自动重启和健康检查。容器启动时会调整挂载的 `./data` 目录权限，随后以非 root 用户运行；不要把其他目录挂载到 `/app/data`。

## 发布

镜像在 GitHub Actions 中构建，并推送到 Docker Hub 的 `mienvirtuoso` 命名空间。首次配置时，在 Docker Hub 创建 `sub2api-console` 仓库并设为 Public。在 GitHub 仓库的 **Settings → Secrets and variables → Actions** 中添加 `DOCKERHUB_TOKEN`，值为 `mienvirtuoso` 账号具有 Read & Write 权限的 Docker Hub Access Token。令牌只保存在 GitHub Secret 中。

版本使用日期标签：当天首个版本为 `vYYYY.MM.DD`，后续版本依次为 `-2`、`-3`，禁止使用 `-1`。创建标签前必须提交 `.github/release-notes/<tag>.md`；具体硬性规则见 [发布说明流程](.github/release-notes/README.md)。

标签推送后，GitHub Actions 会执行完整检查并构建单体 Docker 镜像，发布 amd64/arm64 多架构镜像：

- `mienvirtuoso/sub2api-console:<tag>`

版本镜像通过两个架构的版本与提交校验后，工作流按版本顺序更新 `latest`；首次初始化按发布说明流程完成。重跑复用已发布的同版本镜像，旧版本不能覆盖更新的 `latest`。生产部署需要指定版本时，将 API 和 browser 的 `image` 改为同一个版本标签。

```bash
(cd backend && bash scripts/check-go.sh vet && bash scripts/check-go.sh test)
(cd frontend && bun run test && bun run typecheck && bun run lint && bun run build)
```

后端检查入口会同时运行普通 Go 包和所有模块的 `__tests__` 回归包；直接运行 `go test ./...` 会跳过以下划线开头的目录。

首次克隆仓库后启用提交前检查：

```bash
git config core.hooksPath .githooks
```

`pre-commit` 会先检查暂存区空白错误，再执行与 CI 相同的前端格式检查。检查失败时提交会被阻止；运行 `cd frontend && bun run format` 修复格式后重新暂存并提交。

Console 不提供外部运行库实时读取或同步接口。主动探测只使用 Console 私有配置库中的授权信息和业务库中的账号记录；探测结果写回 Console 业务库。业务写回按当前控制台策略和权限执行，与 skills 数据库没有关联。

### 上游鉴权恢复

“恢复鉴权”支持 Token / 刷新 Token、Admin Key、自定义 Headers、账号密码及密码箱登录，具体选项随上游类型变化。凭据由 Go 后端复核后保存，图片验证码仍通过现有验证码流程处理。

若上游登录要求浏览器人机验证，请在上游网站完成验证并重新登录，再将新的 Token 和刷新 Token 填入“恢复鉴权”。若上游将会话绑定到出口 IP 或 User-Agent，登录环境须与控制台请求保持一致，并在自定义 Headers 中填写对应 User-Agent；不能直接复用不同环境取得的会话。上游仍拒绝时，请联系上游管理员确认支持的接口鉴权方式。

### 账号工作台

`/account-workbench` 依据 [AccountWorkbench GitHub 仓库](https://github.com/MIEnchating/AccountWorkbench) 重新实现。旧工作台模块及接口已移除，不再以早期 Windows ZIP 或旧集成能力作为功能基准。新导航对应原项目的导入账号、账号列表、配置模板、处理记录、自动维护五页。

已重建统一输入及文件上传、账号列表、完整配置模板、授权导入、处理记录和自动维护。模板支持手动创建和后续编辑，也可从线上账号读取；手动模板不要求来源账号，配置按管理目标隔离并校验版本。导入先预览确认，隔离写入并读取核对后启用；处理记录支持继续、取消、删除和私有 JSON 输出。自动维护按分组刷新授权，认证仍失败时使用有效登录资料尝试一次重新授权。运行差异、验证及部署状态以 [GitHub 对齐记录](docs/reviews/account-workbench-github-alignment-2026-09-17.md) 为准。

业务后端使用 Go。模板按管理目标隔离，复制白名单配置并保留十进制精度；统一输入支持 Sub2API/Codex JSON、裸 RT 和邮箱登录资料，导入同批重复保留末项，独立输出不去重。预览绑定 Console 登录会话，公开摘要不包含凭据。共享独立浏览器通过私有 Unix Socket 运行，不开放远程调试端口，不挂载控制台数据目录。

隔离浏览器集成测试可运行 `CONSOLE_TEST_CHROMIUM=/path/to/chrome CONSOLE_TEST_OAUTH_NETWORK_ISOLATED=1 unshare --net go test ./internal/browserlogin/__tests__`（工作目录 `backend`，需要 Xvfb 和创建网络命名空间的权限）。测试只连接本地临时 HTTPS 站点，不连接真实官方服务。
